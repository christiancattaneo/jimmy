Why jimmy

Static scanners read your code. Pen-testers attack the query string. Load tools push until it breaks. None of them reason about who is allowed to see which rows under which session, or whether the data is correct after concurrent writes. jimmy fills that gap, the way Jepsen does for distributed databases but pointed one layer up, at your application's use of the database.

Recipes

In a Supabase project

Point jimmy at your local Supabase database. Read-only by default; the fuzz and anomaly probes use a throwaway transaction.

supabase start
DB=$(supabase status -o env | grep DB_URL | cut -d= -f2 | tr -d '"')

npx jimmy-db scan --db "$DB" --migrations-dir ./supabase/migrations
npx jimmy-db rls fuzz --db "$DB"        # prove tenant A cannot touch tenant B
npx jimmy-db anomalies --db "$DB"       # which isolation anomalies are observable

In CI for migration PRs

The migration linter needs no database, so it runs on every pull request. Record a baseline once so you only fail on newly introduced findings.

# .github/workflows/db.yml
- uses: christiancattaneo/jimmy@main
  with:
    command: migrations
    migrations-dir: supabase/migrations
    fail-on: high

Or with the CLI directly, suppressing the pile of pre-existing findings:

jimmy migrations lint --dir ./supabase/migrations --update-baseline
jimmy migrations lint --dir ./supabase/migrations --baseline .jimmy-baseline.json --quiet

RLS fuzz before deploy

Gate a deploy on tenant isolation. The fuzz seeds two adversarial near-collision tenants in a rolled-back transaction and proves the first cannot read, update, delete, or insert against the second.

jimmy rls fuzz --db "$STAGING_DB" --fail-on critical --history fuzz-history.json
# exit 2 if any tenant boundary leaks
